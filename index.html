A quick, honest read on a site's header posture

Most header scanners tell you whether a control exists. Fewer tell you whether it actually works. Headerscope is built to close that gap.

The problem

Security headers like HSTS, CSP, and cookie flags are some of the cheapest defenses a site can ship — and some of the easiest to get subtly wrong. A CSP full of unsafe-inline and wildcard sources passes most naive checks while offering almost no real protection. An HSTS header with preload but no includeSubDomains looks fine until you try to actually submit it to the preload list.

Teams need a fast way to see not just what's present, but what's actually doing its job, without installing anything or reading RFC text mid-review.

What it checks

  • Strict-Transport-Security — presence, max-age, and real preload-list eligibility
  • Content-Security-Policy — presence, plus unsafe-inline / unsafe-eval / wildcard sources and missing object-src, base-uri, or frame-ancestors
  • X-Frame-Options and clickjacking coverage via CSP frame-ancestors
  • X-Content-Type-Options, Referrer-Policy, Permissions-Policy
  • Cookie flags — Secure, HttpOnly, and SameSite checked independently, across every Set-Cookie header observed
  • HTTPS enforcement and Server header version disclosure

How it works

A Netlify serverless function performs a single read-only GET to the target, server-side — avoiding the CORS restrictions that stop a browser from reading cross-origin response headers directly. Nothing about a scanned URL is stored or logged.

Every request is checked against private, loopback, and link-local IP ranges before connecting, including on redirect hops, and is rate-limited and time-boxed. Full detail on the SSRF handling is in the repo README, rather than asked to be taken on faith.
